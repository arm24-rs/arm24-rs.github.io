An LLM that screens public tenders

I built this tool for ARM24, my sole proprietorship. Every morning it lists the new open IT tenders on Serbia's public procurement portal and tells me which ones are worth reading, with the clause that decides it. It is not a client project. The tender in the walkthrough below is invented.

How it works

  1. ScanA Python script runs at 08:00 every day. It asks the portal's public interface for open tenders with IT codes (CPV 72 and 48), one request per second, and remembers which tenders it has already seen.
  2. Code checks firstClosed tenders, deadlines too close to prepare a bid and estimated values above my limit are dropped in code. No model is called for them.
  3. Pre-filter on namesThe model gets the names of the remaining tenders, 40 at a time, and drops only clear cases: licence renewals, hardware, support of a named vendor product, maintenance of the buyer's existing system, and work that is not software. When it is unsure, it keeps the tender.
  4. Gates check of the documentsFor each kept tender the script downloads the documents and the buyers' questions and answers, converts them to text (at most 400,000 characters) and lists the files it could not read. The model checks seven gates in order and stops at the first one that fails: eligibility, qualification, security, value, submission, delivery and deadline. The rules are a written file, not hidden in the prompt.
  5. One line per tenderThe verdict is fail or unknown, with the gate, a one-line reason and the deciding clause quoted in the original language, with its file name. The tool never says pass: some selection criteria are visible only to a logged-in bidder, so a tender that passes on the public documents is reported as unknown, with what to open next.

How the output is kept honest

  • The model must answer in a JSON schema; verdicts and gate names come from fixed lists. A malformed answer is an error, not a guess.
  • Every verdict carries a quote and a file name, so I check it in a minute instead of reading the whole tender.
  • The model runs headless (Claude Code by Anthropic) with no tools and no network access of its own. The documents are data in its input.
  • Each call has a budget limit and the day has a spend cap. A tender leaves the queue only after its verdict is written; on an error it is retried at the next daily run, up to three times.
  • 54 automated tests run the scan and the triage against saved portal responses with the model replaced by a stub.

Walkthrough with an invented tender

A city sports centre publishes "Development of a web application for booking sports halls", estimated value 2,400,000 RSD, deadline in 12 days. The code checks pass: open, enough time, value within the limit. The pre-filter keeps it: a new build. The gates check reads the tender documents and stops at qualification:

{
  "verdict": "fail",
  "gate": "qualification",
  "reason": "Three references of at least 2,000,000 RSD each in the last three years; a group bid with a firm that has them would pass.",
  "evidence": "„најмање три референце ... појединачне вредности најмање 2.000.000 динара” (konkursna-dokumentacija.pdf)"
}

On 2026-11-25 the portal listed 88 open IT tenders. None passed every gate for my firm: most were written for the incumbent supplier or asked for licences, hardware or a staffed team.

What carries over to a client project

The same pattern fits an LLM feature in your product: plain code decides what code can decide, the model gets written rules and must answer in a schema, every answer points to its source, saved inputs and a stubbed model make the behaviour testable, and spend has a ceiling.
